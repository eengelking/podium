**The end-to-end suite can run in shards (#1130).** `scripts/e2e-all.sh --shards N` splits each database's run into N runs at once, each with its own server, database and Cypress container and a disjoint group of the spec files. The new `scripts/e2e-shards.mjs` computes the groups from the files on disk and checks that every spec is in exactly one. It balances them by the seconds each spec took, recorded in the new `e2e/spec-times.json`, which `node scripts/e2e-shards.mjs --record <logs>` writes from Cypress logs; a spec with no recorded time is weighed at the median, and the script names it. The result line names each shard (`sqlite.2=FAIL(1)`), the specs counted over a database's shards must equal the files on disk, and a run that cannot start (no memory for another container) exits 2 and is never a pass. `scripts/e2e-up.sh` gets a `build` command, so `e2e-all.sh` builds the image once before its runs, and it now exits 2 when the server does not start or the Cypress container is killed. It also logs how long each server restart, pause and resume took, a restart split into its database, server and seed parts, and their count and total at the end of the run. Without `--shards` it is one run per database, as before. `--help`, `podium-e2e-update` and the e2e keeper say how to choose N for a machine, from measured runs: about 1.1 GB per run, so at most the CPUs and at most the memory in GB divided by 2 runs at once, which is `--shards 3` on a 6-CPU, 16 GB podman machine with two databases (about 7m20s against 16m40s for one shard). `scripts/e2e-sample.py` records the host's and each container's CPU and memory beside a run. Tooling only; no app change.
