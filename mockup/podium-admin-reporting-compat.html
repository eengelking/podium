What this mockup proposes

  • One new page, Harness updates, in the Reporting group after Tools. It holds what is new in the issue: features that stopped, and reporters behind the newest version. Every other figure goes where its neighbours already are, as the earlier mockups did: platform and reporter version on People and groups (which already lists reporter versions), slash commands and skills on Tools, projects and branches per person on Usage.
  • Features that stopped. The reporter counts, per session, which hooks fired, which event fields were present and which tool names arrived; the server keeps those as names and counts per harness version per day. A feature is listed against the first version that lost it, with its kind (hook, field or tool name) and what on the console it affects under its name, the share of sessions that sent it before and now, and the reporters on that version. A version with no change shows nothing, and the page says "Nothing has stopped".
  • Compatibility notice (SPEC 6.8). The top bar already says "2 reporters need an update". A second pill, "3 features stopped after a harness update", links to this page. It shows only while Admin is unlocked, because the page is Admin-only, and only when something is listed.
  • Reporters behind the newest version extends the Harness versions table on Tools: the same weeks, with how many reporters were on an older version than the newest Podium had seen for that harness that week, as one neutral-ink chart and a table with a row per harness. Versions are compared only within one harness.
  • All harnesses. Every section covers Claude Code and OpenCode by default, has a Harness filter, and carries a harness column in CSV and JSON. A figure one harness cannot supply shows a dash with the reason (OpenCode reports no skills).
  • Short captions and column names carry the detail in a dotted-underline tip (the existing .tt with a title), so the page reads quickly and the meaning is one hover away.
  • Only names and counts are stored. No arguments, paths, prompts, command text, host names or user names. The platform is the OS and CPU family.
  • How a section is split into panels (a rule the maintainer set with this mockup). A summary row of big figures stays in the same panel as what follows it when that content has no headers of its own, such as a chart (one object, with a rule between). When what follows has headers of its own, such as a table with column headers, it is a separate panel under the same section heading. So "Features that stopped" is a summary panel and a table panel, and "Reporters behind the newest version" is summary and chart in one panel, and the table in a second. It is recorded as a standards changelog fragment (changelog.d/724.standards.md) for podium-standards-update to add to patterns.html at release-prep.
  • Nothing else here is new to the standards: the pill, tables, summary figures, chart, pager and note line all exist, with no :root block and no new class.

Decisions for the maintainer

  • The signal and its threshold (issue checklist). Proposed: listed when at least 25% of the previous version's sessions sent it, under a tenth of that share send it now, and the new version has at least 20 sessions from at least 2 reporters. The numbers keep one machine, a rarely used tool or a quiet week from raising a false alarm, but they also mean a feature used by few sessions can stop without being listed. Agree, or change them?
  • Which names are watched. Hooks the reporter registers and event fields it reads are a closed list, so a drop there is real. Tool names are open (a person may simply stop using WebFetch), so a tool name is listed as Tool name and the page says it may be a habit, not a break. Keep tool names in, or limit the page to hooks and fields?
  • Slash commands and skills. The issue says only if the reporter already sees them. This is drawn on that assumption; the build confirms it per harness, and a harness that cannot see them shows a dash, or the section is left out if neither can.
  • Branch and project names. Drawn as counts, plus the most used project name (already on the wall). Branch names are not listed. Say if you want the names.

What it needs underneath (not drawn)

  • A report field for hook, event-field and tool-name counts per session, sent by every reporter (plugin/core/ for the shared part, each harness for its own hooks). A reporter that predates it sends nothing and is left out of the comparison, and the page says so.
  • A daily summary table of those counts per harness version, kept 395 days like the others. A schema change, made in every storage adapter in the same PR with a contract case in each, and the reporter's OS and CPU family as a column on the reporter row.
