Turning off the single-key shortcuts

The keys \ [ ] and w work anywhere on the page outside a text field, and nothing can turn them off or change them. WCAG 2.1.4 (character key shortcuts) asks that a shortcut made of one printable key can be turned off, remapped, or works only while its control has focus. Someone using speech input, or hitting keys by accident, now collapses a pane or starts wall mode by mistake. Esc is not a printable key, so it needs nothing.

Decided: Option A, a Shortcuts switch in Display settings, off by default. Options B and C were considered and are kept lower down, marked not chosen. Each frame is live: press the switches, then press \ [ ] or w anywhere on this page to see what the option would do. Use the demo bar for dark, light and a 380 px width.

New in this option

Option A (accepted): a Shortcuts switch in Display settings, off by default

Display settings is the row under the top bar that already holds Refresh every and Theme. Both are remembered per browser in localStorage, which is also how the collapsed panes, pins and the Board choice are kept. One more field, Shortcuts, with the same switch Admin uses. Off by default: the frame opens with the keys not working and the pane tips not naming them. Press the switch to see On, the alternate.

Consequence. People who use \ [ ] and w today lose them until they turn Shortcuts on. This is a visible change and goes in the CHANGELOG. A person finds the keys from the switch itself: its hint, shown on hover and keyboard focus and read by a screen reader, names all four.

ShortcutsOff
The switch's hint (hover, focus, screen reader): \ top bar, [ left pane, ] right pane, w wall mode, Esc leaves wall mode. The hover tip on each pane control names its key only while Shortcuts is on. Off, as drawn, it names none.

Pros
  • Meets 2.1.4 by letting the person turn the keys off, on the page where they already choose how the console looks.
  • A person's own choice, not an Admin one: it follows the person who needs it, on their browser.
  • Off by default, nobody is caught by a stray key or speech input before they have chosen.
  • Reuses the Display settings region, the .field and the Admin switch (.sw). No new component.
Cons
  • Off by default, people who use the keys today lose them until they turn Shortcuts on, on each browser. A wall display needs it switched on once.
  • Per browser: someone on three machines sets it three times.
  • The row is hidden when the top bar is collapsed. The bar comes back with the tab (and \, when Shortcuts is on), so the switch is reachable but one step away.
  • History carries the same row (spec 8.1, Theme picker), so the setting would need wiring there too.
  • A new key in localStorage, say podium.shortcuts, and a spec line.

Considered and not chosen

B and C stay here with their pros and cons, so the reasoning is kept. Neither will be built.

Option B (not chosen): a switch in Admin > Settings (everyone on the server)

Admin > Settings holds server-wide switches: Feature flags, Wall notices, The wall. A row here, in The wall, would switch the keys off for every person on this server. It does not conflict with the wall-notice rule: that rule is about informational notes, and this is not a notice. Admin would own the answer for people who may never see Admin.

Pros
  • One place, set once. Fits the existing Admin pattern: a row, a one-line description, an On/Off switch.
  • Suits a shared wall display where one admin wants the keys gone for everyone.
Cons
  • The person who needs the change is rarely the Admin. They must ask, and everyone else loses the keys too. This is the weakest fit for 2.1.4, which is about the person's control.
  • Admin reaches the server through a separate unlock, so a person cannot fix it themselves.
  • Adds an Admin flag (and an atlas row and a server-side store), more than the problem needs.

Option C (not chosen): a modifier key, no setting

Change the keys to Shift plus the key. A shortcut that needs a modifier is not a character key shortcut, so 2.1.4 no longer applies. Nothing to switch, nothing stored. The tips name the new keys. Ctrl, Meta and Alt stay out of it because browsers and screen readers use them.

Shift+\ top bar, Shift+[ left pane, Shift+] right pane, Shift+W wall mode, Esc leaves wall mode. A plain w or [ does nothing.

Pros
  • No setting, no storage, no spec flag. Meets 2.1.4 by design.
  • Stray keys and speech input can no longer fire a shortcut.
Cons
  • Breaks the keys people use now, with no way back. Wall-display users retrain.
  • Shift changes the character: Shift+[ reports { and Shift+\ reports |. The code must match the physical key (e.code), which differs on non-US layouts, so a key can be awkward or missing.
  • Four two-key chords are harder to remember and reach than four single keys.
  • Someone who wanted fewer shortcuts still has them. There is no off.

Decision and open questions

Decision: Option A.
  • A Shortcuts switch in the Display settings row, kept per browser in localStorage.
  • Off by default. People who use \ [ ] and w today lose them until they turn Shortcuts on. This is a visible change for the CHANGELOG.
  • The label is "Shortcuts". Its hint names the four keys.
  • While it is off, the pane tips and the Wall mode button's title do not name the keys.
  • History's Display settings row carries the same switch.

Questions, as answered

  1. Where is a per-person preference kept? Per browser. The spec has no per-person display setting: it keeps theme, refresh interval, collapsed panes and pins per browser in localStorage, and says pins are "not per person and the server does not know about them".
  2. Default on or off? Answered: off.
  3. Label? Answered: "Shortcuts".
  4. When off, do the tips drop the key names? Answered: yes.
  5. Does History's row carry the switch? Answered: yes.
  6. A and C together later? Not chosen.

Not mocked: "active only while a control has focus". The keys exist to collapse panes from anywhere, for example on a wall display with nothing focused, so a focus-only rule would remove their purpose. If you want it drawn, say so.
