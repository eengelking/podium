    What this mockup proposes

    • Where it lives. The issue says "Admin > Data". Since #484 the Admin menu has a Reporting group with a Data kept page, so the setting goes there, as a new Activity history section under the existing detail rows, which gain one row for it. A new page, Stored activity, sits beside it for totals, filters and deleting.
    • The setting is one form with one primary button. The default, "Not stored", is the current behavior, so nobody who leaves it alone sees a change. The other choices are purge after n hours, days, weeks or months; purge when the session ends; keep everything. An optional size cap removes the oldest first. The warning line appears only once a keeping choice is picked, before Save, and says reporters will send more and the server will store more. It also states who can read the history.
    • Stored activity shows the totals first (entries, size on disk, sessions, and how many match the filter), then the filters (session, loop, project, owner, age, source), then the sessions with a tick box. Deleting works three ways: the ticked sessions, everything that matches the filter, or everything. Each one asks first in a warning-bordered box that says how many entries and how much space will go, and offers a button for each answer. After it runs, a line says what was removed and that the Admin log has it.
    • The Source filter has one choice today, Activity. Opt-in recordings (#353, H2) add a second source here without a new screen.
    • The Activity window keeps its place and look. With history kept it shows the newest page of stored entries and a "Show older" row, so a long history pages instead of loading at once. The footer says what is stored ("412 stored entries since 2026-10-12") and when it will go ("Kept until 2026-11-11"). A session that has ended shows its history with no refresh control. Under the default policy the window reads exactly as it does today.
    • Who can read it. Stored history opens for the session's owner and the Admin, the same people who can open a file's diff. Anyone else sees a plain line saying so, never the entries.
    • Nothing new is invented. Every piece is one that exists: the form box, the warning-bordered box, the selection bar, the table with tick boxes, the pager, the modal and the feed list. Status is a shape, a word and a color. Buttons say what they do.
    • A live session. Deleting the history of a session that is still running removes what is stored so far. It keeps capturing afterward while a keeping policy is on, and the confirmation says so when a live session is among those picked.

    Open decisions, with a recommendation

    DecisionRecommendationWhy
    1. Where the data livesA second SQLite file just for activity (and later recordings).A table in podium.sqlite makes backups, vacuum and the hourly sweeper slower as it grows. A second file has its own size, purge cost and backup, with the same dependency. Settle it together with #353, which needs the same store.
    2. Scope of the policyOne global setting for now.Per project or per owner can come later without changing this screen. The form would gain a scope row.
    3. Which entriesEverything the feed shows, including answers and messages sent from Podium, each keeping its marker.A person looking back needs the answers they gave. Storing only what the agent did loses half the story.
    4. RedactionKeep the redaction done before sending. Add no second pass now, and say so on the setting.The text is already cut to 300 characters and scrubbed. The warning line and the owner-and-Admin read rule carry the rest. A second pass can follow if a gap shows.
    5. Size capOffer it, optional, off by default, removing the oldest first.A retention in time can still grow without limit on a busy fleet. The Stored activity totals show whether it is needed.
    6. "Purge when the session ends" against the 30-day session retentionThe shorter of the two wins.A history never outlives the session it describes, and the Admin can see the rule stated on the setting.

    Shared with #353 (recording and replay)

    • The same store, the same purge job (run every few minutes, since both issues allow a retention of hours), the same Stored activity page with a second source, and the same read rule.
    • Not shared: #353's per-session consent, the owner's reporter option, the always-visible recording notice and the replay view. They stay in #353.

    Not drawn

    • The capture itself (reporters sending every running loop), the purge job and the load test. They have no screen. The setting's warning line is the only place Admin sees the cost.
    • The wall and the orchestrator page are unchanged. Opening the window works as it does today.
    • The empty, loading and error states of Stored activity (nothing stored, still counting, the server unreachable) follow the rules on patterns.html under empty, loading and error states.
    • The 400 px frame only narrows the content. The Admin menu collapses by the browser window's width, not the frame's, so check the collapsed menu by narrowing the browser window itself.

    Entries, sessions and numbers are example data. This mockup is static: nothing is read from or written to a server.
