# Releasing Podium

The general sequence is `github-release`, read with its `resources/development-branch.md` (this repo has a `development` branch): the release-candidate gate, `release-prep/<version>` into `development`, the `development` to `main` release PR merged with a regular merge commit, the tag, the hotfix steps and the backport. Do not restate them here. This skill holds only what that skill cannot know about Podium. `PROJECT.md` holds the rules (one version for the whole product, feature PRs never bump it, the maintainer decides on a release).

Where this repo differs from the generic skill:

- **Publish is the docs site, the tracked `dist/` and the reporter archive.** There is no package registry and no container registry; users build the image with `podiumctl build`. The site deploys itself when `main` moves (`.github/workflows/docs-site.yml`), so the generic publish step has nothing to run. The reporter is published by the release PR itself: `dist/claudecode/` and `dist/opencode/` are committed on `main` and `eengelking-marketplace` points at `dist/claudecode` with no `ref` (DECISIONS 60), so merging the release PR is what makes a new version installable. Nothing else publishes it and there is no `plugin-dist` branch. There are two archives: `podium-reporter-<version>.zip` (#835), zipped from the tracked `dist/claudecode/`, and `podium-opencode-<version>.zip` (#857), zipped from `dist/opencode/` with `--harness opencode` (its manifest is `package.json`). `scripts/podium-reporter-zip.mjs` makes them and `.github/workflows/release.yml` attaches them when the `vX.Y.Z` tag is pushed. `release.yml` first runs `scripts/plugin-dist-check.mjs`, fails if the mod's version is not the tag's, and runs `scripts/plugin-dist-compare.mjs`, which fails unless each zip's files and bytes equal its `dist/<harness>/` in the tag's checkout. The nightly prerelease carries its own copy, built from a clean build in its throwaway checkout and never touching the tracked `dist/`, named `podium-reporter-<version>-nightly-<date>.zip` and `podium-opencode-<version>-nightly-<date>.zip`.
- **The marketplace pointer moves with the release.** The entry in `eengelking/skills` changes from `mod/podium-reporter` to `dist/claudecode` (no `ref`, no `sha`). The maintainer updates it at the moment the release PR merges, so a new install fails for seconds at most. After the merge check that `dist/claudecode/.claude-plugin/plugin.json` on `main` has the release's version and that an install from the marketplace works.
- **Tag, then release, then check the asset.** Push the tag and make the GitHub Release right after (`release.yml` waits up to 30 minutes for it). Then check the `Release asset` run is green and `gh release view vX.Y.Z --json assets` lists `podium-reporter-X.Y.Z.zip` and `podium-opencode-X.Y.Z.zip`. If it is missing, re-run the workflow from the Actions tab (`workflow_dispatch`, with the tag).
- **After the release PR merges**, check the `Docs site` run on `main` is green and the new version is in the site's menu (`podium-docs-site`) before proposing the tag.

## The gate for this repo

The generic gate, made concrete. On the tip of `development`:

- `npm test` and `npm run build` pass (CI runs both).
- `npm run plugin:dist:check` passes on the release-prep result: `dist/` is exactly a clean build of `plugin/` at the release version (CI runs it on the PR into `main` and on the push to `main`, and a failure blocks the merge). Order matters: bump the versions, then rebuild `dist/` with `npm run plugin:build:release`, then commit. Any commit that lands on `development` after that makes `dist/` stale, so redo the rebuild in the release-prep PR before opening the release PR. Never run `plugin:build:release` on a feature branch: it rewrites the tracked `dist/`; use `npm run plugin:build`, which builds into `dist-dev/`.
- `npm run standards:parity` passes: the standards must equal the app that is about to become `main` (CI runs it on a PR into `main`). If `changelog.d/` has `standards` fragments (or `[Unreleased]` has `Standards:` lines), load `podium-standards-update` in the release-prep PR and bring `docs/standards/` in line.
- `npm run e2e` passes: the whole end-to-end suite, in containers, with no failure and no retry (the `E2E` workflow also runs on the release PR into `main`, on the self-hosted runners; run it locally first, since a failing spec stops a release).
- `node scripts/check-deprecations.mjs` passes (it is in `npm test`): no row of `docs/DEPRECATIONS.md` "Deprecated now" has a Removed release at or below the version being cut. A due removal is made in its own PR into `development` before `release-prep/<version>` is opened, because release-prep only bumps versions; the removal PR moves the row to "Removed" and adds a `removed` changelog fragment. The check fails the moment the bump reaches the Removed release, so a release-prep PR cannot go green with one overdue.
- All documentation is current, `README.md` first (#1026). Read the README top to bottom against what `[Unreleased]` and the code say now, and fix what is stale before the bump: what the product is, which harnesses it supports and how to install each one's reporter, the quick start, the documentation table and its links. Then do the same for `docs/INTRODUCTION.md`, `docs/REPORTER.md`, `docs/SERVER.md`, the user guide, `CONTRIBUTING.md` and every other page a release entry touches. A claim that is true of one harness only (for example "Claude Code only") is stale the moment a second harness ships. `npm test` and the site build catch dead links and stale indexes, not stale statements, so this is a reading, not a command.
- The docs site builds: `node site/scripts/build.mjs` (the release PR's `Docs site` workflow runs it).
- If the reporter (`plugin/core/` or any `plugin/<harness>/`) changed since the last release, `npm run test:core` and each harness's `test:mod:<harness>` and `typecheck:mod:<harness>` too (today `claudecode`). The harness pairs need that harness's CLI installed and cannot run in CI.

## Files that change in the release-prep PR

All in the same commit, never as a follow-up after the tag. A hotfix changes the same files with a patch bump. `scripts/versions.test.ts` fails if the versions differ.

| File | What changes |
|---|---|
| `changelog.d/` and `CHANGELOG.md` | First run `node scripts/changelog-assemble.mjs`: it appends each fragment to its subsection of `[Unreleased]` and deletes the file, so the rest of the release-prep reads the whole section (DECISIONS 67; `--check` validates the fragments without changing anything). Commit the result, then rename `[Unreleased]` to `[X.Y.Z] - YYYY-MM-DD` and add a fresh empty `[Unreleased]` above it. Update the two links at the bottom (`[Unreleased]` compares `vX.Y.Z...HEAD`; `[X.Y.Z]` points at the release) |
| `package.json`, `server/package.json`, `frontend/package.json` | `version`, all three the new release number |
| `package-lock.json` | Run `npm install --package-lock-only` so its entries follow the manifests |
| `plugin/claudecode/.claude-plugin/plugin.json` (and the version file of any other harness that has one) | `version`, the same release number |
| `plugin/claudecode/hooks/register.ts` | `VERSION`, equal to `plugin.json` |
| `dist/` | Rebuilt after every other row in this table, with `npm run plugin:build:release` (it empties `dist/` first) and committed: the built reporter that the marketplace installs. `plugin-dist-check` fails the PR into `main` if it is stale, and a commit that lands on `development` afterwards makes it stale again |
| `plugin/opencode/package.json` and `plugin/opencode/version.ts` | `version` and `VERSION`, the same release number (`scripts/versions.test.ts` fails if they differ from each other or from the root) |
| `docs/atlas/podium-atlas.html` | The version in the rail ("Reads from the repo at vX.Y.Z") and in the footer ("at version X.Y.Z"); the line counts under "How much is tested", the chart and its table, and the "Counted from the repository on" date, when the release changed much code (`podium-atlas-update`) |
| `server/src/fleet/compat.ts` | On a new **minor or major** only: move `max` in both entries of `REPORTER_SUPPORT` (`podium-reporter-claudecode` and `podium-reporter-opencode`) to the release's `MAJOR.MINOR.0`, or the server tells every up-to-date reporter it is newer than the server supports (SPEC 6.8; `scripts/versions.test.ts` fails for either) |

Then grep the repo for the old version string and look at every hit before assuming the table is complete. Known hits that are sample data and do not change: `docs/fixtures/report.sample.json`, the fixtures in `server/src/fleet/*.test.ts`, `docs/gotchas/`, `plugin/claudecode/hooks/scripted.ts`, the simulator's `0.1.0-sim`, and the manifest example in `docs/spec/`.

`plugin/core/` ships inside every harness, so a change only in `plugin/core/` (not in a `*.test.ts`) changes the reporter: `mod-version-check.yml` requires a `plugin.json` bump for it, and the bump level follows what `[Unreleased]` says. A new harness under `plugin/` adds a row to the table above, a `REPORTER_SUPPORT` entry of its own in `compat.ts` (#852; no entry means no version warning), and a line in `scripts/versions.test.ts`'s harness list if it keeps its version somewhere other than `.claude-plugin/plugin.json` or `package.json`.

A hotfix changes the same files with a patch bump, and rebuilds and commits `dist/` in the same PR (`npm run plugin:build:release`, then `npm run plugin:dist:check`), because the PR into `main` is gated by the same check. A hotfix that changes the UI also updates `docs/standards/` in the same PR (`podium-standards-update`).

## The release check

Run `github-release`'s `resources/release-check.md` (a fresh, non-fork Haiku subagent before the release-prep PR is opened, authority stated in its prompt). It covers the generic checks: the versions agree, the CHANGELOG section and links, the old-version grep, documented numbers, the docs build, tests and the build. Give it the version-file table above as "every file that carries the version", and add these Podium checks:

- the atlas still matches the code: `docs/atlas/podium-atlas.html` carries the release version, every source file it names exists, every handler registered with `on(` in `plugin/claudecode/hooks/register.ts` has a row in `docs/atlas/ATLAS.md` and every hook row there is still registered, and a number the atlas states (a default timing, a limit, a port, a count of pages or migrations) still equals the code, checked for each part an `[Unreleased]` entry touches;
- the archive matches the version: `npm run plugin:build:release` (not `npm run plugin:build`, whose dev stamp the zip script refuses), then `node scripts/podium-reporter-zip.mjs --out <tmpdir> --expect-version X.Y.Z` succeeds and names `podium-reporter-X.Y.Z.zip`, and the same with `--harness opencode` names `podium-opencode-X.Y.Z.zip` (so the tag to come will match the archives `release.yml` builds);
- `dist/` is the clean build of this release: after the version bump, `npm run plugin:build:release` rebuilds it, `npm run plugin:dist:check` passes on the committed result, no built folder holds `.claude-plugin/dev-build.json`, and each harness's manifest `version` equals the root `package.json` `version` (the check fails a mismatch, so catch it here, before the release PR);
- the deprecations are honoured: for each row in `docs/DEPRECATIONS.md` "Deprecated now", Removed is after the release (a row that equals or precedes it must not exist); for each row in "Removed" the feature is gone from the code, `docs/` and the Admin settings, and the `[Unreleased]` or released changelog section has a `Removed` line for it; and a feature that `[Unreleased]` lists under `Deprecated` has a row on the page whose Announced is this release;
- the documentation is current (#1026): read `README.md` in full and report each statement that no longer matches the code or `[Unreleased]`, in particular anything that names one harness where Podium now supports several, an install step for a harness that has none, and a documentation-table row or link that is missing or dead; then do the same for `docs/INTRODUCTION.md`, `docs/REPORTER.md`, `docs/SERVER.md`, the user guide and `CONTRIBUTING.md`. A stale statement in any of them is a failure, and the README is named in the verdict either way;
- the docs site builds for every version (`node site/scripts/build.mjs`), and no link is broken;
- every registered adapter's unit, contract, differential and e2e runs passed on the release commit (`Test with PostgreSQL`, `Test with MariaDB 11.4` and `npm test` for each adapter, and the `E2E` workflow's run on every database in its list; `E2E summary` fails if one is missing or skipped), with nothing in an adapter's `known` list that the release does not allow
- the end-to-end suite passed on the tip of `development` (`npm run e2e`, run locally), and `node scripts/e2e-map.mjs` reports the coverage map true;
- `npm run standards:parity` passes, and the standards were brought in line when `[Unreleased]` has `Standards:` lines (`git diff --stat docs/standards` is not empty then).

Fix every failure and run the agent once more; if the second run still fails, stop and ask. Run `npm test` and `npm run build` yourself too.
