# Updating the Podium end-to-end suite

The suite is Cypress, run in the pinned `cypress/included` container against Podium's own image on a private container network (decision 48). `docs/e2e/COVERAGE.md` is its map and its how-to; read it first. This skill is the procedure for keeping the two true as the console changes.

## Does this change need an e2e update?

Yes, when it changes something a browser can observe: a label, a button, a control, a state, a page, a route the console calls, a setting or Admin flag or reporter option, a default, a layout, a message. No, for a refactor that keeps every behavior, a test-only or docs-only change, a copy change nowhere a spec asserts it (search `e2e/` for the old text first), or a server-internal change with no visible effect. When no spec changes, the PR says so and why.

## Procedure

Work on a branch in a worktree, as for any change (`.claude/CLAUDE.md`, "Always Branch First").

1. **Find what changed.** `git diff origin/development...HEAD`. List each observable behavior added, changed or removed.
2. **Find the specs it touches.** The map in `docs/e2e/COVERAGE.md` points from a feature to its files. Then `grep -rn "<old label or id>" e2e/`. For a removed feature, find everything that names it, including helpers in `e2e/support/commands.js` and the seed in `scripts/e2e-seed.mjs`.
3. **Decide per behavior.** Update an assertion; add a test to the spec file of its area; add a new spec file (one area per file, named for what it covers) and its map row; remove the test, the map row and any seed data or `data-testid` a removed feature leaves behind. If the code and `docs/spec/` disagree on the behavior, do not choose: assert neither and report the contradiction.
4. **Write it the way the suite is written.**
   - `before(() => cy.resetServer())` first: the server restarts on an empty database and is seeded, so a spec file never depends on another. Options: `{ seedArgs: '--bulk 30' }`, `{ env: ['STALE_AFTER_MS=2000'] }`, `{ noSeed: true }`.
   - Select by ARIA role and name, label, an id that is part of the page's contract, or text. A `data-testid` (kebab-case, no data in it, `data-state` for a state a spec waits on) only where none of those singles it out; it is the only app change you may make and it changes nothing a person sees.
   - Sign in with `cy.signIn('Ed')`, `cy.signIn('Admin')`, `cy.unlockAdmin()` or `cy.openAdmin('Settings')`: they set the cookie by request, so the admin secret is never typed or logged. Change what a reporter reports with `cy.reportAgain(key, over, agents, steps)`, flags with `cy.setFlags`, the server with `cy.task('server:pause')` and `server:resume`.
   - Assert with retrying queries. Never `cy.wait(ms)`, a clock-derived value, a count that may still be changing, or a retry (`retries` is 0 on purpose). A value that is live is asserted with `should(...)`, so it retries.
   - Never read a value once and then act on it. `.then()` and `.invoke(...).then(...)` do not retry, so a count that shows `–` until its list loads, or a length that is still growing, fails on a busy machine. Parse or compare inside `should(($el) => ...)` or use a query with a matcher (`contains('button', /^Idle\s*4$/)`). A read once is kept only where what the spec already waited for settles the value, with a one-line comment that says why.
   - Never move on from a click, a type, a select or a blur while the page is still finishing what it started (a write, a redirect, a hash change). Before the next `cy.visit`, `cy.reload` or read of another page, assert what the page shows or the address it ends on, or wait for the write with `cy.intercept(...).as('x')` and `cy.wait('@x')`.
   - New fixed data goes in `scripts/e2e-seed.mjs` with fixed ids, names and costs, through the server's own routes; it must stay restartable. **A new seed session or changed figure must not change what an existing spec reads** (counts of cards, tiles, rail pages, Admin rows): put it behind an option (`--bulk N`, `--ended N`, `--talk`, `--recording`, `--rich`, `--reporters`, `--flags defaults|none|<list>`) and pass it with `cy.resetServer({ seedArgs: '--rich' })`. The default seed's twelve sessions are the contract.
   - Play the reporter mod with `cy.task('diffs:start')` and `diffs:stop` (it answers the console's file-diff requests from `e2e/support/diffs.cjs`), and read exports with `cy.task('download:read', '.csv')`. axe-core is read with `cy.task('axe:source')` through `cy.checkA11y({ known })`; a known violation needs a rule and a target, an issue number in its comment, and is let through only while axe still reports it.
   - Colors are never hard-coded; this suite touches no CSS.
5. **Update the map.** Add or change the feature's row in `docs/e2e/COVERAGE.md`, with the spec file in a code span; a feature that cannot be checked this way goes under "What no end-to-end spec can reach" with the reason. Do not reword other rows.
6. **Run the changed specs first, then the whole suite (at most twice).** A focused run takes minutes; a whole run takes about half an hour and holds the machine's database lock for that time, so the whole run is never used to find a problem a focused run could have found. The loop:
   1. Find the specs that cover the change: the spec files the branch touched or added (`git diff --name-only <base>...HEAD -- e2e/`), the specs `docs/e2e/COVERAGE.md` names for the changed feature, and a `grep -rn` of `e2e/` for the changed label, route or `data-testid`. Run `node scripts/e2e-map.mjs` to check the map. When unsure, include the neighbour specs in the same folder rather than guess narrow.
   2. Run only those, on SQLite first: `npm run e2e:fast -- --db sqlite --shards 1 -- --spec "<file or cypress/e2e/<area>/**>"` (add `--no-build` when the image of this checkout is built and nothing changed since). For a change to `server/src/storage/`, a route or database behavior, run the same focused specs on `--db "sqlite postgres mariadb"` once they pass on SQLite.
   3. Fix a failure at its cause, never by weakening an assertion, skipping a test or adding a wait or retry, and repeat step 2 until the changed specs pass.
   4. Only then run the whole suite (below), the final gate that the focused runs never replace. If it fails, fix the failing specs, re-run only those focused (on the databases that failed) until they pass, then run the whole suite again. That second whole run needs no permission; a third does, so after two whole runs that fail, stop and report. A flaky spec is tracked and never given a retry.
   Focused runs never count as a whole run. Each run, focused or whole, is one command started once: never a second concurrent run.

   **The whole run, as one command started once.** Run it in the background with its output in a log and wait for it to end: no `while`, `until` or `sleep` loops to watch it, because a loop outlives its tool call and is never stopped ("Running commands and cleaning up" in `.claude/agents/podium-e2e-keeper.md`). `npm run e2e:fast` builds the image from the working tree, so the app change is in it, splits the run into shards that run at once, and ends with one `E2E RESULT:` line naming each database and shard (exit 2 is a run that could not start, never a pass). A spec alone: `npm run e2e:fast -- --db <kind> --shards 1 --no-build -- --spec "cypress/e2e/<area>/**"`. Then the whole suite on each database: it must pass with no error and no retry. Which databases: a change that touches no storage adapter, contract, route or database behavior runs the default (SQLite) and needs no `--db`; one specific database to test is `--db <kind>`; a change to `server/src/storage/`, a route or database behavior, or a request for the whole check, is `--db "sqlite postgres mariadb"` (the registered kinds are `DATABASES` in `.github/workflows/e2e.yml`; never name one from memory). The command picks the shard count from the machine and the number of databases (at most 3; three databases on a 6-CPU, 16 GB machine get 2), prints it and why, and ends with one `E2E RESULT:` line naming each database and shard (`sqlite.2=FAIL(1)`); leave `--shards N` off unless you have a reason, because the default already follows the machine, and say in your report which count it chose. After you add specs or change how long one takes, refresh `e2e/spec-times.json` from the logs of a whole run with `node scripts/e2e-shards.mjs --record <out>/sqlite*.log <out>/postgres*.log <out>/mariadb*.log` (a log for every database the run had) and commit it; a spec with no recorded time is weighed at the median and named in the output. The serial `npm run e2e` is the run to reproduce a failure that only shows when sharded, and on a machine too small to shard. A CI failure names its database and shard (`postgres.2=FAIL(1)`): read that shard's log and screenshots in the `e2e-failure` artifact (`docs/e2e/COVERAGE.md`, "Read a CI failure"). The suite takes about 10 to 15 minutes on one database; a run still going after 20 minutes is hung, so read its log and the server container rather than waiting. A failure in a spec you did not touch is a regression or a flaky spec; find out which and say so. Never weaken an assertion, skip a test or add a wait to get green; if an assertion must change, say what and why. The command takes the machine's database lock (`scripts/db-lock.sh`) and waits its turn when another run holds it: give a time estimate before waiting and say when a run was delayed by it, never kill the holder, and never set `PODIUM_DB_LOCK=off` to get ahead (CI is the only place it is off).
7. **Verify the rest.** `node scripts/e2e-map.mjs`, `npm test` (it runs the map check), `node scripts/check-doc-frontmatter.mjs`, `node scripts/check-doc-refs.mjs`, `node scripts/check-doc-links.mjs`. If a `data-testid` was added, `npm test -w frontend`.
8. **Clean up.** Stop what you started, and only that: the run's own processes, then confirm its containers, network and volume are gone (`podman ps -a --filter label=dev.podium.e2e`, `podman network ls`, `podman volume ls`, or docker's). Do not run `npm run e2e:down`, or any cleanup that removes every run's containers on the machine, when anything else may be running: it removes other sessions' too. If a killed run left some behind, remove the ones whose names carry its run id. Nothing is installed on the host: no `npm install` for Cypress, no `~/Library/Caches/Cypress`, no `e2e/node_modules`.
9. **Report** the specs added, updated and removed, the map rows changed, each run's passing and failing counts, and anything not run, any contradiction between code and spec, and any decision for the maintainer.

## Traps

- **Tests that depend on each other inside a file** are allowed only where a file's story is one sequence (the recording spec stops a recording in one test and reads its replay in the next). Say so in a comment.
- **A flag turned off and on again can drop server state** (recordings). A spec that toggles a flag restores it in `afterEach`, or runs on a server of its own.
- **Live entries only show what arrived after a viewer began to watch**, by the entry's `at`: build the entry when you push it, with a fresh id.
- **A report carries the reporter's options.** `cy.reportAgain` starts from the seed's report, so an option a test turns off must be passed again with each later report.
- **Cypress cannot start a real fullscreen**, and the headless window must be at least as wide as the viewport (`--window-size` in `e2e/cypress.config.cjs`); an element past the window counts as covered.
- **A menu that closes on scroll** (Admin > People's Actions) is chosen with `click({ force: true })` after it is checked open, because Cypress scrolls to reach it.
- **Cypress 16 has no `Cypress.env()`.** Use `cy.env(['NAME'])`; the admin secret reaches the browser side only that way.
- **No secrets anywhere.** The admin secret is per run, in a mode-600 file and an env file, and never in a log, a screenshot or an artifact. Seed tokens are fake and new for each database.
