Networking

Who can talk to what, and what stops them

Podium reports travel one way: the session machine opens the connection, and replies carry any instructions back. The server never dials out to a session. How much of that path is encrypted depends on how you deploy it.

Four ways to run it

The request gauntlet

Requests pass an ordered chain of checks before a route sees them. Choose one and run it through. The order is the real middleware order in server/src/index.ts. On port 4318 one filter runs ahead of the rest.

    What the network exposes

    Defaults are local

    • The server binds 127.0.0.1 unless you choose another address: podiumctl --bind (saved as PODIUMCTL_BIND), or the HOST variable when you run the server directly.
    • Inside the container it binds 0.0.0.0; the host side of the published port is what limits access.
    • A Host that is not loopback, the bind address or on PODIUM_ALLOWED_HOSTS gets 403, which blocks DNS rebinding. A server bound to 0.0.0.0 also accepts any IP address, which a page cannot rebind.
    • Behind a proxy, PODIUM_TRUST_PROXY names the hops whose X-Forwarded-* headers count. A wide range lets a client pick its own address.

    Known limits, stated plainly

    • Reading the console needs no token. Anyone who can reach the port can see the wall.
    • The console and Admin are plain HTTP. Use a TLS proxy on an untrusted network.
    • mTLS covers the reporter port only. A stolen config file holds the key, so revoke the certificate.
    • If reporters already existed when TLS was first turned on, plain-HTTP reporters stay allowed until an Admin turns that off. A fresh server starts with it off.
    The reporter mod

    It runs inside Claude Code, and asks permission for everything else

    podium-reporter is a plugin that loads in each Claude Code process. By default it sends session metadata, short excerpts (the first 400 characters of each agent's task prompt and answer) and the last 12 lines of a failed call's output, not transcripts or file contents. The opt-in options send more, and some of it can be file text: the recording, the file diff and Bash output in the activity feed. Most steps up need a switch on the server and a switch with the session's owner; your name, failure explanations and full prompts need only the owner's option. The live activity feed also needs someone watching. Flip them below.

    What stays on the machine

    • The model's thinking text is never sent.
    • Transcripts are never read for the wall. File contents are not sent: git counts the lines of changed files, and only the counts leave the machine. A diff leaves only for its owner, who has the page open, with both the fileDiff option and the Admin's file-diff flag on (both off by default), and only after redaction. The console loads every changed file's diff in the background unless the fileDiffPreload option is set to false.
    • The OS user name is never read, and neither are your git user settings. Git is read for the branch and changed files. The repo name comes from Claude Code's own session repo, falling back to the remote URL and then the folder name. The machine id is a random 12-character string.
    • Secret-shaped text (sk-ant-…, ghp_…, Bearer …) and the values after password=, token= and similar keys become [redacted] before they leave, in prompts, answers, failure lines, activity, questions and recordings. Plan step titles are only cut to length.

    Built so a session never feels it

    • Hooks mostly update an in-memory model, and a timer does the network work. Four things wait: a session waiting on a person, whose respond hook stays open and makes its own calls; a peer tool call, which waits up to 8 s for the timer to send it; session end, which sends a final report inside a 1 s deadline; and the /podium command, which posts its answer at once. Session start, and a prompt in a folder the session has just moved to, also run a few short local commands.
    • An offline server costs backoff, not session speed, except for a messaging tool call, which waits up to 8 s and then reports that Podium cannot be reached.
    • session.end sends a final report inside a 1 second deadline.
    • A new session id after /clear closes the old id and starts over under the new one.
    The server

    A small loop that keeps the live set honest

    The server holds the set of live sessions, stores what it should keep, and pushes changes to browsers. A one-second sweeper decides when a quiet session is stale and when it is gone.

    How long since the session last reported?

    Drag the slider. Timings are the defaults for a session with the mod: stale at 15 s, dropped 60 s later, an ended session lingers 8 s. A session reported only by settings hooks has no heartbeat, so it goes stale after 10 minutes instead.

    The console

    A browser that computes almost nothing

    The UI is React with plain CSS. It renders the server's SessionView and adds only presentation and display totals: card state, whether to offer Respond, sorting, filtering, bands and sums of cost and tokens. Every tab shows the same state; layout preferences (pins, collapse, grouping) are per browser.

    Where data lives

    The most sensitive live data stays in memory

    The fastest way to judge a monitoring tool is to ask where its data goes. Open questions stay in memory, and so do answers and the per-agent live activity lines unless an Admin keeps Activity history or turns on Session recording for a session. Plans, short excerpts of agent prompts and answers, session events (starts, ends, waits, failures; kept 30 days by default) and a failed call's short summary are stored. Pick a place to see exactly what.

    Running it

    One command to start, one version to track

    podiumctl runs the server in a Podman or Docker container, or as a plain Node process. There is no package registry and no cloud service; users build the image themselves.

    Container mode

    • Two-stage Node 24 image, runs as the non-root node user.
    • Named volume podium-data holds both SQLite files.
    • With TLS on, the CA lives on the host in ~/.podium/tls, mounted at /data/tls.
    • Secrets reach the server through the environment rather than the command line.

    Standalone mode

    • Detached node server/dist/index.js with a pid file and a log.
    • The pid file is trusted only if that pid's command line is Podium's.
    • enable writes a launchd plist or a systemd user unit.
    • The mod is not containerized; it posts to the server's URL.
