Process

How a change to the UI is designed, checked and added to these standards.

When a mockup is required

  • Before any new screen, component, pattern or visible change to an existing one. A one-line fix to what is already there does not need one.
  • A mockup shows the screen in the default theme in both light and dark, and at a narrow width. It shows the empty, error and long-text cases where they apply.
  • A mockup links frontend/src/fleet/tokens.css and the app's stylesheets. It does not carry a :root block of its own.
  • The maintainer accepts the mockup before any code is written. It is published as an Artifact for review, and the file stays in mockup/.

Checking a change against the standards

  • Use the podium-standards-check skill for any UI change or mockup. It reports each deviation with the standard it breaks and where. It does not edit anything.
  • The podium-ui-auditor agent runs the same check across the whole app, and also lists what the app does that no standard covers.
  • The standards constrain the global frontend-design and dataviz skills: Podium's tokens and patterns win.
  • npm test fails on a hard-coded color outside tokens.css that is not listed below, on a token nothing defines, and on a theme below the contrast targets.

Changing a standard

  • A feature or fix PR into development that changes the UI does not edit these pages, the same way it does not bump the version. If the maintainer approved a change to a token, a component, a variant or a pattern rule, it adds a Standards: line under [Unreleased] in CHANGELOG.md that names the change and the approval. A change that changes no standard needs no line. Until the release, npm run standards:parity can fail on development because a sample now shows the change.
  • The podium-standards-update skill brings these pages in line with the code that is about to become main, in the release-prep PR, from the Standards: lines and the maintainer's approvals. It only acts on an approved change, and it does not finish until npm run standards:parity passes with no differences.
  • The release PR into main is valid only if the pages match the app. A hotfix that changes the UI updates the pages in the same PR.
  • While a change is on development and not yet in these pages, the check treats the approved Standards: lines as allowed.
  • A new component or pattern is added to the system in the PR that introduces it: a section on the components page and, if it is a rule, a line on the patterns page. It is not invented inside one feature.
